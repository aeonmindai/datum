## What exists

### Mem0 (San Francisco) — the volume leader, structurally single-user
- $24M total: Seed led by Kindred Ventures, Series A led by Basis Set Ventures, with Peak XV, GitHub Fund, Y Combinator; announced 2025-10-28. Angels include Olivier Pomel (Datadog), Paul Copplestone (Supabase), James Hawkins (PostHog), Thomas Dohmke (ex-GitHub), Lukas Biewald (W&B). — https://www.prnewswire.com/news-releases/mem0-raises-24m-series-a-to-build-memory-layer-for-ai-agents-302597157.html (2025-10-28), https://mem0.ai/series-a
- **What it stores**: LLM-extracted natural-language "facts" in a vector store, plus a named-entity graph. Architecture paper describes Mem0 (dense NL memories in vector DB) and Mem0^g (directed labelled graph, entities as nodes, relations as edges). — https://arxiv.org/pdf/2504.19413 (2025-04)
- **Retrieval**: vector similarity + shared-entity boosting; Platform additionally exposes a queryable graph; OSS entities affect ranking only, "there is no separate graph to query". Advanced Retrieval adds keyword search + reranking. — https://docs.mem0.ai/core-concepts/memory-types (read 2026-08-24)
- **Scoping**: four identifiers — `user_id`, `agent_id`, `run_id`, `app_id` (Platform only). At least one required on `add()`. These are **partition keys, not a hierarchy**; there is no "nearer scope wins". — https://docs.mem0.ai/core-concepts/memory-types
- **Memory types are largely vapour, per their own docs**: of the three `MemoryType` enum values, only `procedural_memory` is implemented. `semantic_memory` and `episodic_memory` are "defined in the `MemoryType` enum but never read anywhere else in the codebase… rejected by validation… no documented roadmap." — https://docs.mem0.ai/core-concepts/memory-types
- **Supersession exists and is non-destructive**: the "Dream" layer runs Supersede + Merge on every plan, as part of the add pipeline. Superseded memories are "not deleted and not hidden by default", badged as superseded, and `latest_only=true` returns only current truth; `include_merged=true` returns merged duplicates. "Nothing Dream does is destructive." — https://docs.mem0.ai/platform/features/dream (read 2026-08-24)
- **But the consolidation layer is architecturally single-user**: "Synthesis only looks at memories scoped to a `user_id` alone. Memories that also carry another entity (an `agent_id`, `run_id`, or `app_id`) are left out of a user's synthesis run… to avoid cross-referencing across agents, runs, or apps." Synthesis is Pro+ only, gated at ≥20 memories, 7-day cadence (daily on Enterprise), up to ~24h delay. — https://docs.mem0.ai/platform/features/dream
- **Pricing (read 2026-08-24)**: Hobby free — 10,000 add + 1,000 retrieval requests/mo, **1 project**. Starter $19/mo — 50,000 add + 5,000 retrieval, **1 project**. Pro $249/mo — 500,000 add + 50,000 retrieval, unlimited projects, graph memory, Dream, advanced analytics. Enterprise custom — on-prem, audit logs, SSO. Multi-project support is a $249/mo gate. — https://mem0.ai/pricing
- Self-host: OSS `Memory` class; Platform is managed. 62,590 GitHub stars at read time. Webhooks and memory-expiration (stop surfacing without deleting) exist. — https://docs.mem0.ai/llms.txt

### Zep / Graphiti (US) — the only production system with a real bitemporal model *and* real provenance
- **Bitemporal, four timestamps per fact**: `created_at` (Zep learned it), `valid_at` (event happened), `invalid_at` (event ended), `expired_at` (Zep learned it ended). Valid/invalid ranges are rendered into the context block. — https://help.getzep.com/facts (read 2026-08-24)
- **Provenance is a first-class mechanism, not a metadata field**: "episode associations". Every fact/entity/observation/summary links back to the episodes it was derived from. Episode metadata is *projected* along those associations onto derived artifacts; an edge's "effective metadata" is the deduplicated union of its associated episodes' metadata. Deleting an episode only removes an edge once no associated episodes remain. — https://help.getzep.com/episode-metadata-projection (read 2026-08-24)
- **Governance in the substrate**: RBAC for humans, ABAC policies attached to API keys and UserGroups to limit "what context each agent and Memory MCP user can reach", audit logging, API logging, SOC 2 Type II, HIPAA BAA, BYOK, BYOC. Source-based policies evaluate the same projected effective metadata. — https://help.getzep.com/governance
- **Retrieval**: hybrid — semantic + keyword (BM25) + graph traversal, over three subgraphs (episode / semantic entity / community). Sub-200ms claimed. Facts are the default search target. — https://arxiv.org/abs/2501.13956 (2025-01-20), https://help.getzep.com/concepts
- **Scoping**: `User Graph` (per end-user) vs `Graph` ("a standalone Context Graph for storing up-to-date knowledge about an object or system"), plus threads and documents. Projects are an isolation/billing unit (5 / 10 / unlimited by tier). Flat, not hierarchical. — https://help.getzep.com/concepts
- **Pricing (read 2026-08-24)**: free 10,000 credits/mo; Flex $1,250/yr (page also quotes "$125/month" in the comparison table) — 50,000 credits/mo, 600 rpm, **5 projects**, 5 Memory MCP seats, 10 custom entity/edge types, 1-day API logs; Flex Plus $3,750/yr — 200,000 credits, 1,000 rpm, 10 projects, 15 seats, Observations, custom extraction instructions, webhooks; Enterprise custom (SOC 2, HIPAA BAA, 1-yr audit logs). **1 credit per 350-byte episode**, +1 per additional 350 bytes; retrieval, storage, threads, users and graph storage are 0 credits. — https://www.getzep.com/pricing/
- Named customers on the pricing page: Samsung, Zscaler, HoneyBook, Twin Health, Praktika.ai, Thrive AI Health, Quorum, Aurasell, AGI Inc, plus two anonymised (S&P 500, Nasdaq-100). S&P Global Market Intelligence coverage April 2026. — https://www.getzep.com/pricing/, https://www.getzep.com/analysts/sp-market-intelligence-report/
- **Funding is surprisingly thin for the apparent enterprise traction**: publicly reported total is a $500K seed, March 2024 (YC, Engineering Capital, Step Function). No Series A announced as of 2026-08. Aggregator data may be incomplete. — https://startupintros.com/orgs/zep-ai (2026-07-13), https://pitchbook.com/profiles/company/539323-75, https://tracxn.com/d/companies/zep/__poSadJnSfLWHjz05Xi3U5KwnpCMWSU3aDrihLX_8FLs (2026-06-05)
- Graphiti OSS: 30.3k stars, 3.1k forks at read time. — https://github.com/getzep/graphiti/issues/1489

### xmemory (London) — the only company arguing our exact thesis out loud
- £3m / $4m pre-seed announced 2026-03-19. Led by Fly Ventures, Begin Capital, AAL VC, 33East, Inovia Capital; angels incl. Vadim Barshtak (ex-CTO Miro), Mark Shmulevich, Alexey Dosovitskiy, Konstantin Vinogradov. Founder Alex Petrov. In closed beta at the time of the raise. — https://www.startupmag.co.uk/funding/xmemory-2026-pre-seed-funding/ (2026-03-19)
- **Thesis, verbatim**: "reliable external AI memory must be schema-grounded. Schemas define what must be remembered, what may be ignored, and **which values must never be inferred**… The result shifts interpretation from the read path to the write path: reads become constrained queries over verified records rather than repeated inference over retrieved prose." — https://arxiv.org/abs/2604.27906 (2026-04-30)
- **Architecture**: iterative schema-aware write path decomposed into object detection → field detection → field-value extraction, with validation gates, local retries, stateful prompt control; plus dedup, stateful updates, relations, **provenance and observability**, schema creation/evolution engine, async write queues. Schema language is "XMD". — https://xmemory.ai/, https://xmemory.ai/why/
- **Their own framing of what graph memory gets wrong** is the same critique we hold: "Edges are not truth… the workflow still needs to know which fact is current, validated, and safe to use"; "Writes need contracts — required fields, allowed values, uniqueness rules, and conflict handling"; "Retrieval is not lifecycle — real workflows need deletion, provenance, permissions, schema evolution, and observability around every memory operation." — https://xmemory.ai/why/
- **Explicitly targets multi-agent working state**: "Give agents reliable state for execution plans, task progress, long research findings, and accumulated tool knowledge across multi-agent and long-running workflows" and "Governed agentic workflows… schema-backed RBAC, lineage, debugging, and testing for every memory read and write." — https://xmemory.ai/
- **And they already articulate the projection idea, half-way**: "It can reliably replace an agentic system of record, or run as a **sidecar validation engine with periodic sync to the system of record, so people can review updates before they merge**." — https://xmemory.ai/ (FAQ)
- Benchmarks (all self-run): end-to-end memory 97.10% F1 vs Mem0 87.24 / Cognee 86.18 / Mem0-graph 86.07 / Supermemory 80.49 / Zep 80.16. Extraction: 90.42% object-level, 62.67% output accuracy, above Gemini 3.1 Pro preview, GPT-5.5 high-reasoning, Sonnet 4.6, Opus 4.7. Application-level 95.2%. Claim of "2x+ fewer tokens" rests on a stated 10-reads-per-write assumption. — https://xmemory.ai/why/, https://arxiv.org/abs/2604.27906
- No pricing published. No bitemporality claimed anywhere I could find. Featured in Bessemer's "AI Infrastructure Roadmap: five frontiers for 2026". — https://www.bvp.com/atlas/ai-infrastructure-roadmap-five-frontiers-for-2026

### TencentDB Agent Memory (Shenzhen) — the closest thing to a multi-agent org substrate that exists
- Open-sourced May 2026; MIT; 24,200 stars / 2,226 forks / 694 open issues at read time; >20,000 stars in 90 days; multiple #1 GitHub Trending. — https://github.com/TencentCloud/TencentDB-Agent-Memory (read 2026-08-24), https://www.prnewswire.com/apac/news-releases/tencentdb-agent-memory-tops-20-000-github-stars-in-90-days-launches-team-memory-for-multi-agent-collaboration-302850576.html (2026-08-13)
- **Four asset types, not one memory blob**: Chat Memory (distilled L0 Conversation → L1 Atom → L2 Scenario → L3 Persona), Skill, LLM-Wiki, Code-Graph. A Skill "has versions, resource files, trigger boundaries, execution steps, and validation rules". — https://github.com/TencentCloud/TencentDB-Agent-Memory
- **Governance is the product**: Memory Hub console manages "ownership, versions, status, visibility, usage counts, and Agent bindings in one place"; visibility is `private` / `team` / `restricted` with User/Role/Agent ACLs; two role layers (global System Admin, team Admin/Member); assets are reviewed before being shared and equipped to other agents; you can "view the source, version, and usage of each memory asset". — https://github.com/TencentCloud/TencentDB-Agent-Memory, PRNewswire 2026-08-13
- **Multi-harness by proxy, not by SDK**: "One Proxy, unchanged protocol, zero-code integration — point the Agent's base URL to the Proxy and it's done. No plugin, hook, or MCP server is required." Supported: DeepSeek Harness, Claude Code, Codex, CodeBuddy, WorkBuddy, Hermes, OpenClaw. — https://github.com/TencentCloud/TencentDB-Agent-Memory
- Claimed with OpenClaw: token usage −61.38%, pass rate +51.52% relative, PersonaMem 48% → 76%. Vendor-run.
- Self-hostable in one command (`memory-core` + `memory-hub` + `proxy`), Tencent Cloud VectorDB backend, SQLite/MongoDB alternatives.

### Letta (SF, ex-MemGPT) — genuine multi-agent shared state, mid-migration
- $10M seed Sept 2024 led by Felicis (Sunflower, Essence VC; angels Jeff Dean, Clem Delangue, Cristobal Valenzuela), reported $70M post-money. No Series A announced as of 2026-08. — https://www.prnewswire.com/news-releases/berkeley-ai-research-lab-spinout-letta-raises-10m-seed-financing-led-by-felicis-to-build-ai-with-memory-302257004.html (2024-09-24), https://theagentsindex.com/letta
- **Original model**: Core (always in context) / Recall / Archival tiers, agent rewrites its own memory. Sleep-time compute: a second agent re-represents context during idle time, model-independently configurable. — https://www.letta.com/blog/sleep-time-compute/ (2025-04-21), https://arxiv.org/html/2504.13171v1
- **Shared memory blocks are being deprecated**: "This guide describes one in-context memory block attached to multiple agents using Letta's legacy v1 API. Memory blocks may be deprecated in the future. **We do not recommend building on memory blocks anymore.** Use shared memory repositories for new work, and make a best effort to migrate agents to MemFS." — https://docs.letta.com/v1-sdk/memory/shared-memory (read 2026-08-24)
- **The replacement is Git**: "Each shared memory repository is a Git repository hosted in Letta Cloud and owned by your organization." Attach per agent; agent reads/edits with normal file and Git tools and must commit and push; other agents pull. Repos can also ship skills at `skills/<name>/SKILL.md`. Cloud-hosted agents only. — https://docs.letta.com/concepts/shared-memory (read 2026-08-24)
- **They document the concurrency reality honestly**: `memory_insert` append-only = concurrent-safe; `memory_replace` = "mostly (fails if target string changed)"; `memory_rethink` full rewrite = "No (last-writer-wins)". "Anti-pattern: Multiple agents doing `memory_rethink` on the same block simultaneously leads to lost updates." Recommended mitigation is to designate one owner agent. `read_only` applies to the whole block: "You cannot make a block read-only for some agents but writable for others." — https://docs.letta.com/v1-sdk/memory/shared-memory
- **Pricing (read 2026-08-24)**: Free (3 stateful agents, BYOK); Pro $20/mo (20 agents); API plan $20/mo + **$0.10 per active agent per month** + $0.00015/sec tool execution + pay-as-you-go LLM; Teams Pro $20/seat/mo — "share agents and set access control", "allow agents within your organization to communicate and collaborate"; Enterprise custom (RBAC, SAML/OIDC). — https://docs.letta.com/pricing

### Honcho / Plastic Labs (US) — the only data model that treats humans and agents as the same primitive
- $5.35M pre-seed announced April 2025: Variant, White Star Capital, Betaworks lead; Mozilla Ventures, Seed Club Ventures, Greycroft, Differential Ventures. — https://www.panewslab.com/en/articledetails/0w9rpdwo.html (2025-04-10)
- **Data model**: `Workspace` → `Peers` + `Sessions` → `Messages`; Peers ↔ Sessions is many-to-many. "Peers represent individual users, agents, or entities… **Treating humans and agents the same lets us support arbitrary combinations of Peers** for multi-agent or group chat scenarios." Workspaces give "complete data separation between teams". — https://honcho.dev/docs/v2/documentation/core-concepts/architecture (read 2026-08-24)
- **Perspective is modelled explicitly**: global representations (everything a peer ever said) vs local representations (one peer's view of another). Local reps are **off by default**. This is the closest anyone comes to per-observer belief. — same URL
- **Reasoning layer ("Deriver")**: fact derivation, short summaries every 20 messages, recursive long summaries every 60, peer cards, and "dreaming" (background re-deduction over prior messages). Deriver tasks parallelise but serialise per-peer-representation in message order.
- **Retrieval is a natural-language oracle, not a query**: the Dialectic `/chat` endpoint — "talk to Honcho about any Peer in a workspace"; developers are told to "frame the Dialectic as talking to an expert on the Peer rather than addressing the Peer itself".
- No pricing page resolved (honcho.dev/pricing → 404 on 2026-08-24). Managed instance at api.honcho.dev uses the documented defaults.

## Where it breaks / what it cannot do

### The extraction pipeline is the industry's load-bearing failure, and it is measured
A production user audited **10,134 mem0 entries after 32 days** (one agent, one human, Qdrant, gemma2:2b for 20 days then Claude Sonnet 4.6 for 12). Result: **97.8% junk. 224 survivors, of which only 38 were clean enough to keep as-is.** — https://github.com/mem0ai/mem0/issues/4573 (2026-03-27)
- Junk breakdown: boot-file/system-prompt restating 52.7% ("Operator prefers Telegram" appeared 200+ times), heartbeat/cron noise 11.5%, system-architecture dumps 8.2% (one entry 4,000+ words), transient task state 7.4%, **hallucinated user profiles 5.2%**, identity confusion 3.3%, **security/privacy leaks 2.1% (IPs, chat IDs, file paths, and two sensitive config values that "should never have reached the vector store")**.
- The feedback-loop finding is the architectural one: **808 entries asserting "User prefers Vim", 191 exact copies, for a user who does not use Vim.** "The 2B model hallucinated it once. It got stored. Next session, it appeared in recall context. The extraction model treated it as ground truth and extracted it again… Any hallucination that gets stored once will be re-extracted indefinitely."
- Upgrading the model did not fix it: "A better model follows the extraction prompt more faithfully, which means it extracts more indiscriminately. **The extraction prompt is the bottleneck, not the model.**"
- The five things the auditor says are missing map almost exactly onto our design: feedback-loop prevention, a quality gate between extraction and storage, negative few-shot examples, **a REJECT action** ("Currently the pipeline can ADD, UPDATE, DELETE, or NONE. There is no way to say 'this fact is not worth storing'"), and identity-aware extraction that knows whether the "user" is a human or a process.
- A commenter's top recommendation is our thesis restated: "**Make the pipeline provenance-aware so it can distinguish new user input from recalled memories, system instructions, tool output, and transient runtime state.**"
- The academic backing: Harvard D3 finds "indiscriminate memory storage performs worse than using no memory at all" and that strict pre-storage filtering gave ~10% average performance gain. — https://d3.harvard.edu/smarter-memories-stronger-agents-how-selective-recall-boosts-llm-performance/

### Bitemporality exists on paper faster than it exists in the wire protocol
Graphiti's core `add_episode` accepts `reference_time`; its MCP server does not, and hardcodes `now()`. Separately, MCP `delete_episode` "calls `EpisodicNode.delete`… The `RELATES_TO` edges that were extracted from the episode remain in the graph, **with stale `episodes` arrays pointing at the now-deleted UUID**. `Entity` nodes mentioned only by the deleted episode are also left behind as orphans" — i.e. the provenance graph silently corrupts on retry. The correct cascading `remove_episode` already existed in core and simply was not called. — https://github.com/getzep/graphiti/issues/1489 (2026-05-15)
Read that again in our terms: the market leader in bitemporal agent memory shipped an agent-facing interface that throws away valid-time and leaves dangling provenance. Correct temporal semantics is not something you get by having the columns.

### Writes are where the money burns, and everyone has the same bill
"A single episode can fire many LLM calls: node extraction, deduplication, edge extraction, per-edge resolution, timestamping, and attributes" (https://codepointer.substack.com/p/agent-memory-systems-and-knowledge, 2026-05-28). Graphiti's own quickstart warns "By default, concurrency is set low to avoid LLM Provider 429 Rate Limit Errors" (https://help.getzep.com/graphiti/getting-started/quick-start). Mem0: "every write is an LLM call with a judgement in it, which is both a latency cost and a failure surface — a bad UPDATE silently rewrites something the agent will later rely on" (https://www.digitalapplied.com/blog/open-source-agent-memory-mem0-letta-zep-compared). Zep's credit model prices exactly this: episodes cost, reads are free.
**Implication for us**: an append-only store with mandatory structured provenance is *cheaper* on the write path than these systems, not more expensive, because the expensive part is the LLM adjudicating what to overwrite — and we never overwrite.

### Concurrent multi-agent writes are unsolved even where sharing exists
Letta ships the honest version: last-writer-wins on full rewrites, "designate one agent as the owner for heavy edits", "design blocks so each agent updates their own section. Use timestamps and agent IDs in content." (https://docs.letta.com/v1-sdk/memory/shared-memory). Their answer to this at scale was to give up on shared mutable blocks and hand agents **Git**, with manual commit/push/pull (https://docs.letta.com/concepts/shared-memory). Nobody has CRDT or append-only semantics for shared agent state. Hundreds of concurrent writers is outside every published design.

### Deprecation churn is a real switching cost in this category
- Letta: "We do not recommend building on memory blocks anymore… make a best effort to migrate agents to MemFS." Shared repos are cloud-only; "Local agents use their own MemFS and project files." **[unverified-secondary]** users report a semantic-search regression because MemFS supports grep/glob but not embeddings (https://github.com/letta-ai/letta/issues/3234, 2026-03-20) and a broader deprecation wave of tool rules, templates and filesystem (https://www.letta.com/blog/our-next-phase/).
- Mem0: major-version breaks removed `output_format`, `api_version`, `async_mode`, `enable_graph` (https://docs.mem0.ai/llms.txt). **[unverified-secondary]** the v3 OSS rewrite removed the graph layer entirely (https://codepointer.substack.com/p/agent-memory-systems-and-knowledge).
- Zep: **[unverified-secondary]** Community Edition deprecated April 2025, pushing self-hosters to a three-system stack (https://blog.getzep.com/announcing-a-new-direction-for-zeps-open-source-strategy/).

## What we should steal

1. **Zep's four timestamps, verbatim**: `created_at` / `valid_at` / `invalid_at` / `expired_at`. It is the right decomposition and it is already legible to buyers. — https://help.getzep.com/facts
2. **Zep's episode-association + metadata-projection mechanism.** Provenance as a graph of associations, with effective metadata computed as the union over associated episodes, and access policy evaluated against that same projected metadata. 3. **Zep's cost model.** Charge on ingest bytes, make reads free. It aligns price with our actual cost (write-path validation) and it makes exact-first retrieval free to hammer, which is exactly the behaviour we want. — https://www.getzep.com/pricing/
4. **xmemory's write-path decomposition**: object detection → field detection → field-value extraction, with validation gates and *local retries* rather than one big structured-output call. Their measured result (90.42% object-level, beating one-shot frontier structured output) is the argument for our "reject the write" server behaviour. Also steal "which values must never be inferred" as an explicit schema declaration. — https://arxiv.org/abs/2604.27906
5. **Mem0's read flags.** `latest_only=true` / default (active + superseded) / `include_merged=true` is a clean, minimal API for "current truth" vs "full history" that does not require the caller to understand bitemporality. Steal the ergonomics; keep our stronger guarantee underneath. — https://docs.mem0.ai/platform/features/dream
6. **Devin's `Promote to Enterprise` and repo pinning.** Explicit, user-visible scope promotion, plus a three-state applicability (no repo / this repo / all repos). This is the shipped precedent for our scope ladder, and it proves buyers understand it. — https://docs.devin.ai/product-guides/knowledge
7. **Devin's mandatory trigger description.** Every knowledge item must declare when it applies. That is a required field enforced at write time — the same discipline we want for provenance. — same URL
8. **TencentDB's asset governance columns**: owner, version, status, visibility (`private` / `team` / `restricted` with User/Role/Agent ACLs), usage count, agent bindings, and source — all in one console, with a review step before an asset can be shared. Also steal their "cold start / load the save file" framing (import repos, docs, and prior agent sessions) — it is the best answer to the empty-store problem I have seen. — https://github.com/TencentCloud/TencentDB-Agent-Memory

## What we should deliberately do differently, and why

1. **No LLM adjudicates an overwrite. Ever.** Every system here has an LLM deciding ADD/UPDATE/DELETE at write time, and every documented catastrophe traces to that decision: silent rewrites, the 808-copy Vim hallucination, "a bad UPDATE silently rewrites something the agent will later rely on". Append-only with explicit supersession removes the class. *Why differently:* Mem0's Dream retains superseded records but still lets an LLM decide *what supersedes what*; we require the writer to name the superseded id.

2. **Provenance is a required field, and the write fails without it. Do not make it optional metadata.** Zep gets provenance by derivation (episode → fact) and it works, but it means provenance is an artefact of the pipeline rather than a contract with the writer — which is why Graphiti's MCP layer could throw away `reference_time` without the type system objecting. Devin proves buyers accept a mandatory field (trigger description). *Why differently:* server-side rejection is the only mechanism that survives contact with a hundred agents written by different people at different times.

3. **Confidence must be an enumerated taxonomy, not a float.** Nobody in this market has any confidence concept at all — measured / confirmed-by-human / derived / unverified does not exist anywhere I looked. A float invites averaging and thresholding, which reintroduces fuzziness. An enum is queryable, filterable, and non-negotiable at write time. *Why differently:* this is genuinely unoccupied ground; it is also the thing that makes "retrieval never returns a bare number" enforceable rather than aspirational.

4. **Contradictions become objects, not silent invalidations.** Zep "attempts to invalidate" the old fact automatically; Mem0's Supersede marks the older fact outdated automatically. Both are *resolution by guess*. Two live records asserting different values for the same metric should raise a contradiction that a named party must resolve, with the resolution itself an assertable, provenanced record. *Why differently:* every automatic invalidation is an LLM judgement call executed without review, and Zep's own graph shows the failure (Kendra's Adidas fact "attempts" invalidation and spawns two new facts — the resulting state is inference, not record).

5. **Scopes resolve, they do not merely isolate.** In Mem0, Zep, Cognee and Supermemory, "project" and "workspace" are billing and isolation units — Cognee literally charges $5/workspace, Mem0 gates multi-project at $249/mo, Zep caps at 5/10 projects. There is no read path from project B to a fact learned in project A. Devin's `Promote to Enterprise` is the only shipped scope-promotion in the category and it is a manual move, not a resolution rule. Global → project → mission → agent with nearest-scope-wins is our differentiator, and it is the thing the coding-agent products' users most obviously need (Cursor: "your teammates never see them").

6. **Exact-first must be a contract with a name, not a hybrid ranker.** Zep's hybrid search and Mem0's advanced retrieval both blend semantic, keyword and graph signals into one score, so the caller cannot tell whether an answer was matched or guessed. xmemory validates the direction — "reads become constrained queries over verified records" — but sells it as accuracy, not as a guarantee. We should make it typed: an exact result and a fuzzy result are different shapes in the response, and the fuzzy channel is labelled at the schema level, not in the docs.

7. **Ship an agent registry with heartbeats. This does not exist anywhere.** Every product here indexes *content*. None indexes *actors*. Letta's answer to N agents is `client.blocks.agents.list(block_id)` (who is attached to this block) — reachability, not liveness. TencentDB's "agent bindings" is the closest, and it is a static assignment. With hundreds of worktrees and branches, discovery and liveness are the actual operational problem, and it is a moat because it is unglamorous.

8. **Missions with reached/not-reached gates. Also does not exist.** Honcho has sessions, Letta has agents, TencentDB has "tasks", Devin has folders. Nobody has a target with a pass/fail predicate. This is what makes the store answerable ("are we there?") rather than merely searchable.

9. **Tracker as projection — take the contrarian side deliberately, and know you are contrarian.** The entire market is running the *other* way (see Q3). The steelman for their direction is real: "issue trackers already encode most of what an autonomous agent needs: structured state, clear ownership, permission hierarchies, and immutable history" (https://www.mindstudio.ai/blog/issue-trackers-ai-agent-infrastructure-jira-linear, 2026-05-03). Our counter is that trackers give you all of that *without valid-time, without confidence, and without a rejection gate* — a Jira field will happily hold an unsourced number forever. Ship a read-only projection first and let people keep Linear as the human surface; do not ask anyone to abandon their tracker on day one. xmemory's "sidecar with periodic sync to the system of record, so people can review updates before they merge" is the migration path that a buyer will actually accept.

10. **Do not compete on LoCoMo, DMR, or STaRK.** The Zep-vs-Mem0 exchange (84% → 58.44%, prompt tampering, single vs 10 runs, denominator error) is what this genre looks like from the outside, and xmemory's own blog title concedes it. Publish (a) production junk rate over 30 days, (b) percentage of returned facts carrying full provenance, (c) percentage of writes rejected and why, (d) point-in-time query correctness under backfill — the exact thing Graphiti #1489 shows is broken. Every one of those is a number a competitor would have to re-architect to match.

11. **Do not build an ingest-connector business.** Graphlit raised $3.56M and became 30 connectors; Cognee's differentiator is 38 sources; Supermemory sells Gmail/Granola/Drive connectors by tier. Connectors are a commodity treadmill and they are the vector by which unprovenanced junk enters the store. Ingest should be a narrow, typed, provenance-bearing API, and connectors should be somebody else's problem.

12. **Do not put the memory on the developer's laptop.** Pieces raised $13.5M for 9 months of on-device workstream memory and it is architecturally incapable of being a shared substrate; Basic Memory's local-first design is honest but the same. Remote and multi-tenant from line one.

## Positioning answers

### Q1 — Which support MANY AGENTS sharing one memory, versus one user / one assistant remembering things?

**Genuine multi-agent shared state (5):**
- **Letta** — org-owned Git-backed shared memory repositories attached per agent, plus legacy shared blocks with documented per-operation concurrency semantics; Teams Pro explicitly "allow agents within your organization to communicate and collaborate". Weakness: last-writer-wins, cloud-only, manual commit/push/pull. — https://docs.letta.com/concepts/shared-memory, https://docs.letta.com/pricing
- **TencentDB Agent Memory** — team-level memory hub; assets owned, versioned, reviewed, ACL'd and *equipped* to named agents; one proxy serves seven different agent harnesses. Best-in-class today. — https://github.com/TencentCloud/TencentDB-Agent-Memory

- **Zep** — non-user `Graph` objects are standalone and any number of API keys can read/write them, with per-key ABAC deciding what each agent may reach. Sharing is real; agent *identity* is only an API key. — https://help.getzep.com/concepts, https://help.getzep.com/governance

### Q2 — Which support cross-PROJECT linkage (facts learned in A reusable in B), and how?

**No — projects are isolation boundaries, and they are monetised as such:**
- **Mem0** — multi-project support is a Pro ($249/mo) feature and there is no documented cross-project read; `app_id` is another partition key. — https://mem0.ai/pricing
- **Zep** — 5 / 10 / unlimited projects by tier; a fact lives on a graph and the only cross-graph mechanism is writing to more than one graph. — https://www.getzep.com/pricing/

## Verdict — closest competitor, and exactly where it stops short

**Zep.** Not xmemory, not TencentDB. Zep is the one to beat.

Zep already has three of our load-bearing pieces, shipped, documented and sold to Samsung and Zscaler:
- true bitemporality with four distinct timestamps, not two;
- provenance as a first-class association graph, with an API to walk it in both directions;
- and — the part I did not expect — **authorisation derived from provenance**: episode metadata projects onto every derived fact, and ABAC policies on agent API keys evaluate that projected metadata. That is our "scopes and governance" story, already in the substrate.

It also has multi-project isolation, sub-200ms retrieval, SOC 2 / HIPAA / BYOK / BYOC, and a credit model that prices writes and gives away reads. If we ship a bitemporal provenanced store with governance and no more, we have built a worse Zep.

**Where it stops short — precisely:**

1. **No confidence.** Nothing in Zep distinguishes a measured value from an LLM's inference from a human's confirmation. Every fact on every edge is presented with identical epistemic status. There is no rejection gate: `graph.add` accepts prose and the pipeline invents the structure.
2. **Supersession is a machine's guess, not an assertion.** Zep "attempts to invalidate" the prior fact. There is no contradiction object, no unresolved state, no named resolver. When the LLM guesses wrong, the graph is silently wrong and the only trace is an `invalid_at` you did not set.
3. **Retrieval is hybrid, not exact-first.** Semantic + BM25 + graph collapse into one score. A caller cannot tell whether an answer was retrieved or approximated. That is the precise failure mode we exist to remove, and it is Zep's default read path.
4. **Scopes isolate, they do not resolve.** `User Graph` and `Graph` are flat siblings; projects are a billing tier capped at 5 or 10. There is no global → project → mission → agent ladder and no nearest-scope-wins. A fact learned in project A is unreachable from project B by construction.
5. **Agents are API keys.** Zep indexes content, never actors. There is no agent registry, no worktree or branch node, no heartbeat, no liveness. Its answer to "which of my two hundred agents is alive and on which mission" is "check your key list".
6. **No missions.** No target, no reached/not-reached gate, no answering "are we there". Threads and documents are containers, not objectives.
7. **No projections.** Zep has webhooks (Flex Plus and up, billed at ⅛ credit). Not an event log you can rebuild a Linear board from. Nothing treats a human tool as a rendered view.
8. **And its bitemporality is not honoured end-to-end.** Graphiti's MCP server — the interface an agent actually speaks — discards `reference_time` and corrupts provenance on delete. Having the columns is not having the semantics. That gap, in the market leader, is the single best proof that our thesis is a build and not a wrapper.

Two footnotes on the runners-up. **xmemory** is closer to our *argument* than Zep is — write-time validation, "which values must never be inferred", reads as constrained queries, provenance and lineage, and even a half-formed projection story — but it has no bitemporality, no append-only guarantee, no scope hierarchy, no registry, no missions, and £3m and a closed beta behind it. It is the company most likely to converge on us; watch it, and assume its founder has read the same papers. **TencentDB Agent Memory** is closer to our *org shape* than anyone — team hub, agent bindings, ownership/version/visibility/source per asset, human review before sharing, one proxy for seven harnesses, 24k stars in three months — but it is a vector store underneath with no bitemporality, no confidence, and no exact-first contract, and it is Tencent, which limits its reach into Western enterprises and simultaneously means it will never be short of money.

The honest summary: **three different competitors each own roughly one third of our shape, and not one of them owns two.** That is the strongest possible signal that the combination is real and unbuilt — and the strongest possible warning that the combination is the only thing we are selling. Bitemporality alone is Zep. Write-time validation alone is xmemory. Team governance alone is Tencent.
