# Research: bitemporal + provenance storage engines and data models

Slice: `bitemporal-provenance`. All claims carry URLs. Negative findings are marked as such.

---

## What exists

### 1. Datomic — accretion-only 5-tuples, reified transactions, as-of queries

A Datomic database is a set of immutable *datoms*: `[entity, attribute, value, transaction, added?]`. There is no update-in-place; a "change" is a retraction datom plus an assertion datom in a new transaction. <https://docs.datomic.com/data-model.html>

The critical structural feature for us: **transaction ids are themselves entity ids**, so a transaction can carry arbitrary attributes. Datomic's own docs give the exact pattern we want — a `:correction/for` attribute on tx 1235 pointing at tx 1234, recording that this transaction fixes a prior mistake. Datomic explicitly frames this as "a system might record domain-specific provenance information associated with each transaction." Same URL.

Query surface: `as-of` (point-in-time), `history` (all assertions and retractions ever), `since`, and a `log` index sorted by time. <https://docs.datomic.com/data-model.html>, <https://jepsen.io/analyses/datomic-pro-1.0.7075>

Architecture: transactors (write, index, one active at a time with standby failover via heartbeat written into storage), peers (thick clients that read storage directly and cache immutable tree nodes), pluggable storage (DynamoDB, Cassandra, Postgres…). Commit = write new immutable tree nodes, then a compare-and-set on a root pointer under Sequential consistency. <https://jepsen.io/analyses/datomic-pro-1.0.7075>, <https://docs.datomic.com/operation/deployment.html>

Scale evidence, real: Nubank (Datomic's owner) "offers financial services to nearly 94 million users, processing an average of 2.3 billion user transactions per day. Almost all of their products use Datomic as a system of record." <https://jepsen.io/analyses/datomic-pro-1.0.7075>

Erasure escape hatch: **excision**. `:db/excise` removes datoms from index *and* transaction log across all of history. Datomic is emphatic that excision is only for privacy/retention, "should never be used to correct erroneous data… as it does not restore any previous view of the facts." Excision records are themselves un-excisable, so you always know that you forgot. <https://docs.datomic.com/operation/excision.html>

### 2. XTDB v2 — bitemporality as the default, not a feature

XTDB 2.0.0 went GA on 2025-06-12. Every table is a SQL:2011 bitemporal table with four automatic temporal columns (`_valid_from`, `_valid_to`, `_system_from`, `_system_to`); queries default to "now" unless you ask otherwise, and non-valid historical rows are filtered at the lowest level of the scan. Postgres wire-compatible, MPL-licensed, Apache Arrow on-disk. <https://docs.xtdb.com/intro/what-is-xtdb.html>, <https://github.com/xtdb/xtdb/releases/tag/v2.0.0>

Write model is deliberately serial: "transactions for each database are processed by a single leader node… writes for a given database happen once, on a single thread… **This design implies a hard upper limit on transaction throughput**, but the key advantage is the concrete information guarantees about exactly when, how & why data across the database has changed." Their words, their docs. <https://docs.xtdb.com/intro/what-is-xtdb.html>

Transaction-level provenance exists and is first class: `BEGIN READ WRITE WITH (METADATA = …)` (v2.1+) attaches arbitrary metadata to a transaction, surfaced in `xt.txs.user_metadata` — the docs literally suggest "upstream request IDs, correlation IDs, or other data lineage information." There is also `ASSERT <predicate>, '<message>'` which rolls back the transaction if a precondition fails, and `ERASE FROM <table> WHERE …` for irrevocable GDPR deletion across all valid- and system-time. <https://docs.xtdb.com/reference/main/sql/txs.html>

The storage design is the single most useful engineering artifact I found for building this ourselves. James Henderson's three-part series, part 3 in particular: <https://www.xtdb.com/blog/building-a-bitemp-index-3-storage>
- Separation of storage and compute over object storage; nodes coordinate *only* through the tx log (Kafka) and the object store, no node-to-node chatter.
- Measured constraint: "it takes roughly the same time to download a 1-10MB file as it does for a 1-10kB file" from object storage. Files target ~100MB.
- In-memory ingest into a hitchhiker-tree/HAMT (branching factor 4, leaf split at 1024), flushed as immutable, *deterministic* L0 files (deterministic so two nodes producing the same file produce identical bytes — no coordination needed).
- LSM compaction that **concats rather than collapses** versions, because "XT is the database that remembers everything."
- Compaction is 4-files-in → 4-files-out, sharded by entity-id hash prefix, so file sizes stay flat and there are enough fine-grained tasks that uncoordinated nodes rarely duplicate work.
- The key index insight: **"recency"** — collapse valid-time and system-time into one scalar, "the maximum timestamp T for which the row was believed valid for both valid-time = T and system-time = T". It may over-estimate but never under-estimate, so you can take the max recency of a whole file and elide the entire file from any as-of-now query. This replaced a 6-dimensional k-d tree that "wasn't as performant as we needed to either update or query."
- Level-1 split on the "Lindy effect": rows still current when they leave L1 go to a *survivor* partition sharded by entity-id; rows already superseded go to a *historical* partition sharded by recency. Sensor data grows the historical side wide; user profiles grow the survivor side deep.

XTDB v1 (formerly Crux) is a different product: a bitemporal *document* store, last on the 1.24.x line with its own docs site at <https://v1-docs.xtdb.com/>. v2 is a hard break — transaction functions were removed entirely and Java <21 dropped from in-process nodes. <https://github.com/orgs/xtdb/discussions/4383>, <https://github.com/xtdb/xtdb/releases/tag/1.24.0>

### 3. SQL:2011 temporal — what the standard actually gives you, and who implements it

**MariaDB** is the most complete open implementation: system-versioned tables, application-time periods, and bitemporal tables combining both. `CREATE TABLE t (x INT) WITH SYSTEM VERSIONING` with pseudo-columns `ROW_START`/`ROW_END`, plus `FOR SYSTEM_TIME AS OF | BETWEEN … AND … | FROM … TO … | ALL`. <https://mariadb.com/docs/server/reference/sql-structure/temporal-tables/system-versioned-tables>, <https://mariadb.com/docs/server/reference/sql-structure/temporal-tables/bitemporal-tables>

A trap worth knowing: MariaDB writes a history row for **every** `UPDATE` whose `SET` list mentions a versioned column, "regardless of whether any column value actually changes." `UPDATE t SET x = x` creates history. See MDEV-23446, same URL.

**SQL Server** has system-versioned temporal tables since 2016, but the limitation list is long: the history table cannot have a primary key or any constraints; `TRUNCATE TABLE` is blocked while versioning is on; direct modification of the history table is forbidden; `INSTEAD OF` triggers are forbidden on both tables; indexed views over `FOR SYSTEM_TIME` queries are unsupported; merge replication is unsupported and transactional replication only works with a single subscriber, "due to a dependency on the local system clock, which can lead to inconsistent temporal data." No application-time periods. <https://learn.microsoft.com/en-us/sql/relational-databases/tables/temporal/considerations-limitations>

**PostgreSQL 18** got the *application-time* half of SQL:2011 and nothing else. The `CREATE TABLE` grammar now has `UNIQUE (…, col WITHOUT OVERLAPS)`, `PRIMARY KEY (…, col WITHOUT OVERLAPS)`, and `FOREIGN KEY (…, PERIOD col) REFERENCES t (…, PERIOD col)`. There is **no** `PERIOD FOR SYSTEM_TIME`, no `WITH SYSTEM VERSIONING`, no `FOR SYSTEM_TIME AS OF` in the grammar. <https://www.postgresql.org/docs/18/sql-createtable.html> Jungwirth confirmed on -hackers that he was doing "the application-time (aka valid-time) side of this, and there is another patch for system-time" — the system-time patch did not land. <https://postgrespro.com/list/thread-id/2556588>, background: <https://aiven.io/blog/exploring-how-postgresql-18-conquered-time-with-temporal-constraints>

**Snowflake Time Travel** is retention-window PITR, not bitemporality: `AT | BEFORE (TIMESTAMP | OFFSET | STATEMENT)`, `UNDROP`, and zero-copy clones at a past timestamp. Retention is **1 day standard, max 90 days on Enterprise**, after which data moves to Fail-safe and is no longer queryable. Retention costs storage. <https://docs.snowflake.com/en/user-guide/data-time-travel>

### 4. Rich Hickey — accretion / relaxation / fixation

The framing from the Spec-ulation keynote (Clojure/conj 2016). "Growth" decomposes into three non-breaking moves:
- **Accretion** — "I am going to provide you more."
- **Relaxation** — "you either require less from people that call you, or provide more to people that call you."
- **Fixation** — "just actually fixing the implementation of something without changing its interface."

"If software only uses growth, only uses those techniques, it is always OK to use a newer version." **Breakage** is the complement: "when you require more from your consumers… or you provide less on the return." <https://github.com/matthiasn/talk-transcripts/blob/master/Hickey_Rich/Spec_ulation.md>, restated in <https://github.com/matthiasn/talk-transcripts/blob/master/Miller_Alex/DependencyHeaven.md>

The operational rule that falls out: don't mutate a thing, name a new one. "Suppose you want to make a backwards-compatibility breaking change to a function. Don't mutate the function… give the function another name." And if the change is systematic across many functions, "create a new namespace and put all the functions there." <https://blog.ezyang.com/2016/12/thoughts-about-spec-ulation-rich-hickey/>

This maps onto our schema/predicate evolution directly, and it is the *only* discipline I found that makes an append-only store survive schema drift without an upconverter graveyard. See "What we should steal."

### 5. Nanopublications — the closest existing thing to our record shape

A nanopublication is four RDF named graphs bound as one atomic, content-addressed unit:
- **Head** — declares the nanopub URI and points at the other three.
- **Assertion** — the claim itself.
- **Provenance** — "how this came to be": `:assertion prov:wasDerivedFrom :experiment . :assertion prov:wasAttributedTo orcid:… .`
- **Publication info** — metadata about the nanopub as an object: creator, `dct:created`, license.

<https://nanopub.net/guidelines/working_draft/>, <https://nanopub.net/>

The well-formedness criteria are the part that matters most to us, because they are **enforced structurally, not by convention**. A nanopub is well-formed only if: exactly one `hasAssertion`, exactly one `hasProvenance`, exactly one `hasPublicationInfo` quad in the head; all five URIs distinct; **every triple lives in exactly one of the four graphs**; "Triples in [P] have at least one reference to [A]"; "Triples in [I] have at least one reference to [N]". A nanopub without provenance is not a nanopub. That is a server-side write rejection, which is exactly the property we want. Same URL.

Immutability is by content-addressing: **Trusty URIs** embed a cryptographic hash of the normalized content into the identifier itself (`http://example.org/pub1/RA-0Yc_l8rK3_Ts8y7kPuZvg6FqzaOSSq0yMSS9Sg4R9I`), so tampering is detectable and the id *is* the integrity check. Kuhn & Dumontier, ESWC 2014: <https://doi.org/10.1007/978-3-319-07443-6_27>

Scale, real numbers: a dump of **10,803,231 nanopublications** was retrieved from the server network on 2018-04-05 <https://research.vu.nl/en/datasets/nanopublication-dump-from-server-network>. Measured replication capacity of the (older) server network was "around 9.4 million new nanopublications per day or 3.4 billion per year" <https://peerj.com/articles/cs-78/>. The second-generation Nanopub Registry replaced the legacy nanopub-server; the legacy servers now only hold old unsigned nanopubs. <https://nanopub.net/docs/architecture/>, live registry: <https://registry.knowledgepixels.com/>

The theoretical basis is Carroll, Bizer, Hayes & Stickler, "Named graphs, provenance and trust", WWW 2005 — <https://doi.org/10.1145/1060745.1060835>.

### 6. PROV-O and RDF-star / RDF 1.2

**PROV-O** is the W3C Recommendation (2013-04-30) encoding the PROV data model in OWL2: Entity / Activity / Agent, `wasDerivedFrom`, `wasGeneratedBy`, `wasAttributedTo`, `used`, `actedOnBehalfOf`. <https://www.w3.org/TR/prov-o/> It is a vocabulary, not an enforcement mechanism.

**RDF-star → RDF 1.2.** Quoted triples were proposed by Hartig & Thompson in 2014 to express statements about statements, and became popular partly as an RDF↔property-graph interop bridge. <https://www.w3.org/2025/04/rdf-star-wg-charter.html> RDF 1.2 Concepts is now at Candidate Recommendation <https://www.w3.org/TR/rdf12-concepts/>. The final design is *not* the original quoted-triple design: a **triple term** is the object of an `rdf:reifies` triple, whose subject is a **reifier**, and annotations attach to the reifier, not to the triple term. New vocabulary (`rdf:TripleTerm`, `rdf:ttSubject`, `rdf:ttPredicate`, `rdf:ttObject`) was introduced rather than reusing `rdf:Statement`, deliberately, because `rdf:Statement` "is known to be found in widely used datasets (e.g. Uniprot)". <https://www.w3.org/TR/2025/WD-rdf12-concepts-20250225/>

### 7. Wikidata — the only production KG I found with a first-class "this is superseded / this is wrong" primitive

Every statement carries a **rank**: `preferred`, `normal`, `deprecated`. Deprecated means "known to include errors… or outdated knowledge (information that was never correct, but was at some point thought to be)". Crucially, deprecating is preferred over deleting, for three stated reasons: it stops other users re-adding the value, it "provides a mechanism for representing the evolution of theories and ideas", and it keeps the KB a secondary source that reports what its sources say. Reasons are machine-readable via qualifiers `P2241` (reason for deprecated rank) and `P7452` (reason for preferred rank), and disputes are recorded with `P1310` (statement disputed by). <https://www.wikidata.org/wiki/Help:Ranking>

Query semantics follow: WDQS materializes a `wikibase:BestRank` view (preferred if any exist, else normal) as the truthy `wdt:` predicate; deprecated statements "will never be used unless that is specifically requested". Same URL. That is precisely the "nearer/stronger record wins, but nothing is deleted" retrieval model we want.

Note explicitly: rank is **not** a dispute-resolution mechanism. "Ranks are not a way of asserting your view for a disputed value, but instead are used for communicating the consensus opinion." Disputes go to a talk page — i.e. Wikidata detects nothing automatically and resolves contradictions socially. Same URL.

### 8. Google Knowledge Vault — the confidence-scored fusion approach, and why it's a cautionary tale

Dong et al., KDD 2014. Fuses noisy web extractions with priors from Freebase, using a multi-layer probabilistic model that separates *source error* from *extraction error*, producing calibrated probabilities of fact correctness. Evaluated over **2.8 billion extracted triples**, estimating the trustworthiness of **119 million webpages**. <https://www.cs.ubc.ca/~murphyk/papers/kv-kdd14.pdf>, <https://research.google/pubs/knowledge-vault-a-web-scale-approach-to-probabilistic-knowledge-fusion/>

It was never a product. Google told Search Engine Land it "was a research report, not an active Google service", and the term disappeared from Google's vocabulary after 2015. <https://searchengineland.com/hold-horses-knowledge-vault-just-research-project-now-204549>, <https://en.wikipedia.org/wiki/Google_Knowledge_Graph>

### 9. Truth maintenance systems and belief revision

**JTMS/ATMS.** de Kleer's ATMS labels each derived node with the set of minimal *environments* (sets of assumptions) supporting it; environments entailing a contradiction are marked **nogood** and dropped. <https://dekleer.org/Publications/Problem%20Solving%20with%20the%20ATMS.pdf>

The blow-up is structural, not an implementation bug: "if we are given n assumptions, there are 2**n possible selections… that is 2**n environments." <https://cis.temple.edu/~ingargio/cis587/readings/tms.html> Retraction is worse than assertion: when you remove a justification, "nogoods which it subsumed have to be put back and every label of every node is potentially affected. For these reasons, directly removing a justification is a bad idea." <https://www.academia.edu/16674638/An_assumption_based_TMS>

**AGM belief revision** (Alchourrón, Gärdenfors, Makinson 1985). Three operations on a logically closed belief set K: *expansion* (add, remove nothing), *contraction* (remove p, remove as little else as possible), *revision* (add p, remove whatever is needed for consistency). Partial-meet contraction is characterized by six postulates: Closure, Success, Inclusion, Vacuity, Extensionality, Recovery. <https://plato.stanford.edu/entries/logic-belief-revision/>

Two things in that entry are directly load-bearing for us. First, **Recovery is the most contested postulate** and it fails for *belief bases* (sets not closed under consequence) even though it holds for belief sets — and a fact store is a belief base, not a belief set. Second, AGM is "input-assimilating": "No explicit representation of time is included." An AGM revision operator and a bitemporal log are answering different questions. Same URL.

### 10. SLSA / in-toto — provenance actually enforced on write, in production, at ecosystem scale

The one place where "no provenance, no write" is a shipping, adopted reality. A SLSA v1 provenance is an in-toto Statement with `subject` (the artifact digests), a `buildDefinition` (`buildType`, `externalParameters`, `internalParameters`, `resolvedDependencies`) and `runDetails` (`builder.id`, `invocationId`, `startedOn`/`finishedOn`, `byproducts`). <https://slsa.dev/spec/v1.0/provenance>

Two design decisions worth copying verbatim:
- **Trust is typed at the field level.** `externalParameters` "are untrusted; they MUST be included in the provenance and MUST be verified downstream"; `internalParameters` "are trusted because the platform is trusted… need not be verified downstream." A provenance record that does not say which parts are trusted is not doing its job.
- **Resolved dependencies carry content digests, including `gitCommit`.** The example resolves `repository: …/hello-world, ref: refs/heads/main` (a *parameter*) into `uri: git+https://github.com/octocat/hello-world@refs/heads/main, digest: {gitCommit: 7fd1a60…}` (a *dependency*). Same URL. Our "evidence: repo, commit" field should be a digest-bearing ResourceDescriptor, not a string.

### 11. Distribution and hosting

**Postgres LISTEN/NOTIFY.** `NOTIFY` takes `AccessExclusiveLock` on "database 0" during `PreCommit_Notify`, held until after commit — a **global mutex serializing every COMMIT on the entire Postgres instance**, not just those using NOTIFY. Recall.ai traced three production outages (2025-03-19 to 2025-03-22) to it; the signature was database load spiking while CPU and disk I/O *plummeted*. They removed their single NOTIFY code path in under a day and the problem vanished. <https://www.recall.ai/blog/postgres-listen-notify-does-not-scale>, source: <https://github.com/postgres/postgres/blob/a749c6f/src/backend/commands/async.c#L956> A core fix (commit `282b1cde`, Joel Jacobson) has landed — <https://github.com/postgres/postgres/commit/282b1cde9dedf456ecf02eb27caf086023a7bb71> — but it is not in any released major version; DBOS benchmarked the optimized path at up to 60K stream writes/sec <https://www.dbos.dev/blog/postgres-listen-notify-scalability>.

**Neon.** Branches are copy-on-write clones; child-branch writes are stored as deltas and "creating a branch does not increase load on the parent branch." Instant restore and branch-from-the-past are bounded by a project-wide **history window**. <https://neon.com/docs/introduction/branching> Hard numbers: 10 branches/project on Free and Launch, 25 on Scale, hard ceiling 5,000/project, extra branches $1.50/branch-month; history window 6 hours (Free) / 7 days (Launch) / 30 days (Scale); logical data size up to 16 TB/branch; 100 projects (Free/Launch), 1,000 (Scale). <https://neon.com/docs/introduction/plans> Scale-to-zero suspends after 5 minutes idle and "reactivates automatically within a few hundred milliseconds"; on paid plans it can be disabled, on Free it cannot. <https://neon.com/docs/introduction/scale-to-zero>

**Cloudflare D1.** Max database size **10 GB, and "the 10 GB limit of a D1 database cannot be further increased."** Each D1 database is a single Durable Object and "is inherently single-threaded, and processes queries one at a time" — "if your average query takes 1 ms, you can run approximately 1,000 queries per second." 50,000 DBs/account by default (raisable to millions), 1 TB/account, 30-day Time Travel PITR, 2 MB max row, 100 bound params/query, 100 columns/table. <https://developers.cloudflare.com/d1/platform/limits/>

**Durable Objects.** 10 GB storage per object; unlimited objects; "Each individual Object is inherently single-threaded" with "a soft limit of 1,000 requests per second"; exceeding storage returns `SQLITE_FULL` on writes while reads and deletes keep working. <https://developers.cloudflare.com/durable-objects/platform/limits/>

**ElectricSQL.** Read-path sync engine over standard Postgres ≥14 via logical replication; clients consume *shapes* over plain HTTP so a CDN can cache them; the Electric service is an Elixir container that persists shape logs to local disk and wants NVMe ("disk speed — low latency, high throughput reads and writes" is priority #1, above memory and CPU). Compaction of shape logs is not implemented yet (<https://github.com/electric-sql/electric/issues/1582>). Works with Neon and Supabase. <https://electric.ax/docs/sync/guides/deployment>

**Convex.** Reactive document-relational DB where queries are TypeScript running in the database; queries auto-subscribe and are re-run when their read set changes; mutations are serializable-isolation OCC transactions with automatic retry; clients get all subscriptions updated to "a singular moment in time in the database". Cloud Convex "runs on top of PlanetScale using MySQL as its persistence layer"; OSS runs on SQLite/Postgres/MySQL. <https://docs.convex.dev/understanding/overview>

**Turso / libSQL.** Now positioned as an embedded SQLite-successor engine with push/pull sync to cloud, plus "AgentFS — filesystem and state SDK for AI agents with built-in auditability," plus Turso Cloud with branching. <https://docs.turso.tech/introduction>

**NATS JetStream** — subject-wildcard streams with server-side retention; a stream captures e.g. `orders.>` and new subjects under that prefix require no reconfiguration. <https://docs.nats.io/nats-concepts/jetstream/streams>

**Redis Streams** — append-only log with monotonically increasing IDs (`XADD` rejects non-increasing IDs), consumer groups with a per-group pending-entries list, `XACK`, `XCLAIM`/`XAUTOCLAIM` with a delivery counter for failure recovery, and capped streams via `XADD MAXLEN`/`XTRIM` (with `~` for cheap approximate trimming). <https://redis.io/docs/latest/develop/data-types/streams/>

**Automerge** — JSON-shaped CRDT documents: maps, RGA lists, peritext-based rich text with marks, and grow-only Counters. <https://automerge.org/docs/reference/documents/>

## What is proven vs claimed

**Proven.**
- Datomic's inter-transaction safety is *stronger* than advertised. Jepsen: "every history [was] Serializable… sessions bound to a single peer appear Strong Session Serializable, and histories restricted to write transactions and reads using `d/sync` appear Strong Serializable." That is an independent audit, funded by Nubank, published with the raw test suite. <https://jepsen.io/analyses/datomic-pro-1.0.7075>
- Accretion-only at real scale works: 94M users, 2.3B user transactions/day, Datomic as system of record. Same URL.
- The LISTEN/NOTIFY global lock is proven by source code plus a reproduced load test plus three dated outages. <https://www.recall.ai/blog/postgres-listen-notify-does-not-scale>
- Nanopublication structural validation is a real, implemented, machine-checkable spec with a decade-old running server network and an eight-figure corpus. <https://nanopub.net/guidelines/working_draft/>, <https://research.vu.nl/en/datasets/nanopublication-dump-from-server-network>
- MariaDB/SQL Server system-versioning are shipping, documented, and their *limitations* are documented — which is itself evidence of maturity. <https://learn.microsoft.com/en-us/sql/relational-databases/tables/temporal/considerations-limitations>
- ATMS exponential blow-up is a theorem, not a benchmark artifact: 2^n environments for n assumptions. <https://cis.temple.edu/~ingargio/cis587/readings/tms.html>

**Claimed but not independently verified.**
- XTDB v2's throughput. XTDB's docs state a "hard upper limit on transaction throughput" but publish no number for it. I found **no** Jepsen report and **no** published TPS benchmark for XTDB 2.x. The recency/Lindy sharding heuristics are argued from first principles in a blog post with diagrams, not with benchmark tables. <https://docs.xtdb.com/intro/what-is-xtdb.html>, <https://www.xtdb.com/blog/building-a-bitemp-index-3-storage>
- "Zero-cost, full database snapshots" (XTDB release notes) is a marketing framing of "as-of queries against an immutable index" — zero *marginal storage* cost, not zero query cost. <https://github.com/xtdb/xtdb/releases/tag/v2.0.0>
- Datomic never published TPS figures either. The docs point you at `TransactionMsec` and `TransactionBytes` metrics and tell you to pipeline; that's it. <https://docs.datomic.com/operation/monitoring.html>
- Google Knowledge Vault: calibrated confidence at 2.8B triples was demonstrated in a paper and then abandoned. Treat the *architecture* as evidence and the *viability* as unproven. <https://searchengineland.com/hold-horses-knowledge-vault-just-research-project-now-204549>
- Neon's "few hundred milliseconds" cold start is a vendor claim on a vendor docs page with no percentile breakdown. <https://neon.com/docs/introduction/scale-to-zero>

**Vapour / not what it sounds like.**
- "Provenance-enforcing knowledge graph" is mostly aspiration. Wikidata is the largest KG with statement-level references and **it does not enforce them**: measurements put coverage at ~68% of statements with at least one reference <https://researchportal.hw.ac.uk/files/53252708/Reference_Statistics_in_Wikidata_Topical_Subsets_corrected_version.pdf> (a different 2024 count says >73% have provenance metadata, the discrepancy coming from counting distinct reference *nodes* vs statements). And coverage ≠ quality: the RQSS study scores overall Wikidata referencing quality at **0.58 out of 1**. <https://www.semantic-web-journal.net/content/rqss-referencing-quality-scoring-system-wikidata>, <https://journals.sagepub.com/doi/10.3233/SW-243695>
- RDF-star as a stable statement-level metadata standard is not yet real. RDF 1.2 Concepts is still CR <https://www.w3.org/TR/rdf12-concepts/>; the WG's own issue tracker says "definition of reifiers is non-normative and seems vague" <https://github.com/w3c/rdf-star-wg/issues/169>; and "SPARQL 1.2 support for querying triple terms varies across stores. Jena/Fuseki is ahead; many commercial stores are lagging" <https://ontologist.substack.com/p/rdf-12-vs-neo4jopencypher>. Vendors are still shipping pre-standard encodings: GraphDB/RDF4J serializes embedded triples to older clients as `urn:rdf4j:triple:<base64>` IRIs. <https://graphdb.ontotext.com/documentation/11.3/rdf-sparql-star.html>
- No production system I could find automatically raises a **contradiction object** for two live records disagreeing on the same metric and requires resolution. Wikidata comes closest and is explicitly a manual, social process. Nanopublications have no contradiction concept at all — anyone can publish a nanopub asserting the opposite and both stand. This is a genuine gap, and it is the most defensible thing in our proposed design.

## Where it breaks / what it cannot do

### Accretion-only stores

- **Erasure is an out-of-band, expensive, whole-database operation.** Datomic: "Excision puts a substantial burden on background indexing. Large excisions can trigger indexing jobs whose execution time is **proportional to the size of the entire database**, leading to back pressure and reduced write availability. Try to avoid excising more than a few thousand datoms at a time on a live system." It is also not transactional (background, at next indexing job), not recoverable, cannot excise `:db/fulltext` attributes, and cannot guarantee full removal for `:db/noHistory` attributes. <https://docs.datomic.com/operation/excision.html>
- **Single-writer is the price of a total order.** "Using a Sequential CaS operation ensures a global order of transactions, and limits Datomic's write throughput to the speed of a single transactor." <https://jepsen.io/analyses/datomic-pro-1.0.7075> XTDB makes the same trade explicitly. <https://docs.xtdb.com/intro/what-is-xtdb.html>
- **The single writer is operationally fragile.** Jepsen found Datomic transactors "kill themselves when they cannot maintain a stable connection to storage… When we ran transactors with the default 5-second timeout settings on nodes outside AWS, transactors routinely killed themselves every few minutes due to normal network fluctuations. With a 1-second timeout, even transactors running in our EC2 test environment would kill themselves roughly every 10–20 minutes." Datomic's answer is "run your own supervisor daemon." <https://jepsen.io/analyses/datomic-pro-1.0.7075>
- **Semantics inside a transaction can be surprising.** Datomic executes all operations in a transaction *as if concurrent*: two `[:db/cas 123 :v 0 1]` in one transaction both succeed; two calls to an `increment` transaction function produce `1`, not `2`; a lookup ref cannot see an entity created earlier in the same transaction. Jepsen demonstrated **"pseudo write skew"**: an `approve` and a `deny` transaction function, each individually correct and each checking "not already approved or denied", produce a grant that is *both approved and denied* when called in the same transaction, because their write sets are disjoint so the conflict checker doesn't fire. Nubank considers this expected behaviour and will not change it. Same URL. **This is a direct warning for us**: a "supersede" operation and a "contradict" operation in the same batch can each individually preserve an invariant and jointly break it.
- **Retention is not history.** Snowflake caps at 90 days (Enterprise) and drops to Fail-safe after <https://docs.snowflake.com/en/user-guide/data-time-travel>. Neon's history window caps at 30 days on Scale <https://neon.com/docs/introduction/plans>. D1 Time Travel caps at 30 days <https://developers.cloudflare.com/d1/platform/limits/>. None of these are a bitemporal store; they are backups with SQL syntax. "What did we believe on Aug 19" is unanswerable in all of them past the window.

### Event sourcing / CQRS — the specific failure modes we must design against

These are the ones with production war stories attached. This is where such systems die.

1. **Projector/domain drift.** "At some point somebody will replace, split or merge one or more events in the domain and forget to update the corresponding projections. And this is exactly what happened to us, more than once." <https://www.dennisdoomen.com/2017/11/the-ugly-of-event-sourcingreal-world.html>
2. **Projectors reading other projectors.** Rebuilding projection A while it silently reads projection B, which sits at a completely different point in the log, yields a rebuilt projection with plausible-looking wrong data and no crash. Doomen hit this twice; "it took us quite some time to figure out why the rebuilt projection contained some unexpected data." Same URL.
3. **Non-idempotent emitters producing unbounded streams.** A background job updating an aggregate without an idempotency check emitted an event per run; months later a single stream had **>100K events**, writes to that entity had degraded to unusable, and the diagnostics page timed out. They had to delete the entire stream and rebuild projections. Same URL.
4. **Log ordering that isn't.** SQL Server IDENTITY columns can complete **out of order**, so a projector reading by sequence number can process event N+1 before event N. It only showed up "after months of regular load testing" and only under high load. Fixes: an exclusive lock on insert, or gap detection with page reload. Same URL. Any sequence we hand out must be gap-detected or gap-free by construction.
5. **Batching + idempotency = resurrection bugs.** Batching projections across a transaction boundary, plus crash, plus replay from an earlier offset, plus create-on-first-reference, produced projections re-materialized with default values that blew up on NOT NULL constraints. Same URL.
6. **Event schema evolution vs. immutability.** "You are left with a choice between updating all the existing events or handling multiple schemas in your code… If you want to preserve the immutability of events, you will be forced to maintain processing logic that can handle every version of the event schema. Over time this can give rise to some extremely complicated programming logic." <https://www.ben-morris.com/event-stores-and-event-sourcing-some-practical-disadvantages-and-problems/> Doomen has an event postfixed `V5` and warns that "unless you test your projectors against every earlier incarnation of an event… the only thing you can do is to document your events properly."
7. **Historical fidelity is lost the moment you rewrite or up-cast.** "As soon as you take it, you've lost the ability to accurately produce the state of your system at the point in time of the rewrite." The "100% accurate audit log" claim "ends up suffering from a case of 'nope' once you get past the conceptual / toy stage." <https://chriskiehl.com/article/event-sourcing-is-hard> **This is the single most dangerous failure for us**, because "what did we believe on Aug 19" is our headline product claim.
8. **The raw event stream as public API destroys encapsulation.** "In practice, this manages to somehow simultaneously be both extremely coupled and yet excruciatingly opaque… you'd never let two separate services reach directly into each other's data storage when *not* event sourcing." Plus opacity: you lose the ability to reason about which system consumes what. Same URL.
9. **Conflating event-sourced with event-driven.** Pryce's team used the event store as a message bus; the history filled with technical events ("attempt to send email failed with an IOException") that users didn't care about and that had to be filtered out of every user-facing history view. "We realised we'd made a mistake when we had to make entities distinguish between reading an event in order to react to it, and reading an event in order to know what happened in the past." <http://natpryce.com/articles/000819.html>
10. **Eventual consistency you didn't ask for.** Pryce: "Initially we gave the event store an HTTP interface… that meant that clients couldn't process events in ACID transactions and we found ourselves building mechanisms in the application to maintain consistency." They reverted to direct DB connections with serializable transactions and kept HTTP only for peripheral, tolerant consumers. Same URL. Kiehl on materialization lag: "Newly created data will 404, deleted items will awkwardly stick around, duplicate items will be returned." <https://chriskiehl.com/article/event-sourcing-is-hard>
11. **Replay cost grows without bound.** A financial app storing every price tick had to replay 3 TB to reconstruct balances, with query times in minutes. <https://kitemetric.com/blogs/event-sourcing-fails-5-real-world-lessons> Snapshotting fixes this but "requires an asynchronous process to create snapshots in advance of any expected query load. In the real world this can be difficult to predict." <https://www.ben-morris.com/event-stores-and-event-sourcing-some-practical-disadvantages-and-problems/>
12. **Support blindness.** "In a generic event store payloads tend to be stored as agnostic payloads in JSON… This can obscure data and make it difficult to diagnose data-related issues… A fix for a support incident might also require a change to data. This is not straightforward for an event store as committed events are supposed to be immutable. You can issue a new event that corrects the data, but this will only correct *future* calculations. Any calculations from a previous point will continue to include the bad data." Same URL. Note this is *by design* for us, but our UI must make it obvious, or every operator will file it as a bug.
13. **Explanation tax.** "Event stores are an abstract idea that some people really struggle with. They come with a high level of 'explanation tax' that has to be paid every time somebody new joins a project." Same URL. For a product we intend to *sell*, this is a go-to-market risk, not just an engineering one.
14. **Every projection is an N-fold multiplier on change cost.** "That first extra projection you add doubles the amount of code that touches your event stream… If you add, modify, or remove an event type, you're on the hook for spreading knowledge of that change to N different places." <https://chriskiehl.com/article/event-sourcing-is-hard>

### Provenance and truth-modelling

- **PROV-O has no teeth.** It is an OWL vocabulary. Nothing in <https://www.w3.org/TR/prov-o/> rejects a write. Enforcement has to be ours.
- **Nanopublications are structurally strict and semantically empty.** The spec requires that the provenance graph *exist* and *reference the assertion*. It says nothing about the provenance being adequate, honest, or of a particular type. `:assertion prov:wasAttributedTo :me` satisfies every well-formedness criterion. <https://nanopub.net/guidelines/working_draft/>
- **Nanopublications are immutable to a fault.** Trusty URIs make them tamper-evident, which means a nanopub cannot be corrected — only superseded by another nanopub, with retraction/supersession handled by convention above the core spec. There is no built-in "this supersedes that" in the four-graph model. Same URLs.
- **RDF-star has a semantics trap.** Per GraphDB's docs on the formal semantics of RDF-star, "each embedded triple also asserts the referenced statement" — so annotating a statement you *don't* believe accidentally asserts it. This is exactly backwards for a contradiction store. <https://graphdb.ontotext.com/documentation/11.3/rdf-sparql-star.html> The RDF 1.2 reifier indirection exists partly to fix this, and it isn't finished.
- **RDF 1.2 graph merging is not safe yet.** "Merging a Full RDF graph containing at least one triple term with a classicized RDF graph… could result in a 'hybrid' graph that cannot be transformed to a consistent Full nor Classic RDF graph." <https://www.w3.org/TR/2025/WD-rdf12-concepts-20250225/>

### Contradiction and belief

- **ATMS is unusable at our scale.** 2^n environments, and retracting a justification potentially dirties every label in the network. <https://cis.temple.edu/~ingargio/cis587/readings/tms.html>, <https://www.academia.edu/16674638/An_assumption_based_TMS> Mitigations exist (CATMS label compression, BF-ATMS focusing, possibilistic ATMS) but all trade completeness for tractability. <https://arxiv.org/pdf/2407.06400>
- **AGM does not model time and Recovery fails for us.** AGM revises a logically closed belief set with no temporal index; our store is a belief *base*, and Recovery — "all the original beliefs are regained if one of them is first removed and then reinserted" — "holds in the AGM model but not in closely related models in which the belief state is represented by a belief base that is not closed under logical consequence." <https://plato.stanford.edu/entries/logic-belief-revision/> Do not build an AGM revision operator and call it bitemporal.
- **Wikidata proves that unenforced provenance decays.** ~68% coverage, quality 0.58/1, and reference coverage was **1.3% in October 2015** on one measurement. A decade of community effort got it to two-thirds. Optional provenance will not be supplied. <https://researchportal.hw.ac.uk/files/53252708/Reference_Statistics_in_Wikidata_Topical_Subsets_corrected_version.pdf>, <https://www.semantic-web-journal.net/content/rqss-referencing-quality-scoring-system-wikidata>

### Hosting

- **Postgres LISTEN/NOTIFY at fan-out scale is a footgun in every released Postgres.** Global commit serialization, ~8,000-byte payload cap, no persistence, and notifications are lost on disconnect. <https://www.recall.ai/blog/postgres-listen-notify-does-not-scale>
- **Neon's branch model does not map onto hundreds of git worktrees.** 10 branches/project (Free/Launch), 25 (Scale), extras at $1.50/branch-month, hard cap 5,000/project. <https://neon.com/docs/introduction/plans> With hundreds of agents each holding a worktree, per-worktree Neon branches means either bill shock or hitting the cap. Branching also loses session state — "prepared statements, advisory locks, and notifications and listeners defined using NOTIFY/LISTEN only exist for the duration of the current session and are lost when the session ends", and scale-to-zero closes idle sessions. <https://neon.com/docs/reference/compatibility>
- **Neon scale-to-zero is incompatible with a sub-10ms read SLO** unless disabled (paid plans only), which forfeits the cost benefit. <https://neon.com/docs/introduction/scale-to-zero>
- **D1 cannot hold the org-wide fact store.** 10 GB hard cap that "cannot be further increased", single-threaded per DB, ~1,000 qps at 1ms/query. <https://developers.cloudflare.com/d1/platform/limits/> A single Durable Object is likewise 10 GB and ~1,000 req/s soft. <https://developers.cloudflare.com/durable-objects/platform/limits/> These are per-tenant/per-worktree shards, not a global store.
- **ElectricSQL needs a stateful disk and a CDN.** Persistent NVMe required, shape log compaction not yet implemented (unbounded disk growth for long-lived shapes) <https://github.com/electric-sql/electric/issues/1582>, replication slot + on-disk state must be cleaned up in lockstep or you corrupt the deployment, and it can't run behind most connection poolers. <https://electric.ax/docs/sync/guides/deployment>
- **Convex is a whole-backend commitment.** Queries are TypeScript in the database, mutations must be deterministic (no network calls), and cloud persistence is PlanetScale/MySQL. <https://docs.convex.dev/understanding/overview> Adopting it means our storage model *is* Convex's model; we would be building a bitemporal store on top of a system that owns the transaction and reactivity layer.
- **CRDTs solve a problem we don't have.** Automerge's RGA/peritext machinery exists to merge *concurrent edits to shared mutable structures*. <https://automerge.org/docs/reference/documents/> Our records are immutable, append-only, and identified by content — two agents asserting different values is not a merge conflict to be auto-resolved, it is a **contradiction we are contractually obliged to surface**. A CRDT here would silently do the exact thing we are selling against.

## What we should steal

1. **The nanopublication quad shape, enforced at write.** Assertion + provenance + publication-info + head, with the well-formedness rules as a server-side validator: provenance MUST reference the assertion, pub-info MUST reference the record, every triple/field belongs to exactly one part. This is a spec we can implement in a day and it gives us "a write without provenance is rejected" for free. <https://nanopub.net/guidelines/working_draft/>
2. **Trusty-URI-style content-addressed ids.** Hash the canonicalized record and put the hash in the id. Tamper-evidence, dedup, deterministic cross-node agreement, and idempotent writes all fall out of one decision. <https://doi.org/10.1007/978-3-319-07443-6_27>
3. **Reified transactions carrying provenance, not per-row provenance columns.** Datomic's `:correction/for` on the transaction entity, and XTDB's `BEGIN READ WRITE WITH (METADATA = …)` → `xt.txs.user_metadata`, are the same idea: batch-level provenance amortizes cost and gives you "why did this batch happen" for free. Keep record-level confidence, hang the heavy evidence off the transaction. <https://docs.datomic.com/data-model.html>, <https://docs.xtdb.com/reference/main/sql/txs.html>
4. **XTDB's `recency` heuristic and Lindy-split sharding.** Collapsing (valid_from, valid_to, system_from, system_to) into one over-estimating scalar so that as-of-now queries can elide entire files is the single best idea in the whole slice for hitting sub-10ms hot reads over an accretion-only store. Pair it with the survivor/historical split at L1. <https://www.xtdb.com/blog/building-a-bitemp-index-3-storage>
5. **Wikidata's three-rank model as the retrieval default.** `preferred` / `normal` / `deprecated`, with a machine-readable *reason* qualifier on each non-normal rank (`P2241`-equivalent), and a materialized `BestRank` view that is what normal queries hit. Deprecation instead of deletion, with the stated rationale that it stops re-adding the bad value and preserves the evolution of belief. <https://www.wikidata.org/wiki/Help:Ranking>
6. **SLSA's typed-trust provenance fields.** Split evidence into "asserted by an untrusted party, MUST be verified downstream" vs "produced by the trusted platform". And make repo/commit evidence a digest-bearing resource descriptor (`uri: git+https://…@ref`, `digest: {gitCommit: …}`), not a free-text string. <https://slsa.dev/spec/v1.0/provenance>
7. **Hickey's accretion/relaxation/fixation as the *schema* governance rule.** Predicates, scopes, and confidence enums may only grow, relax, or be reimplemented. A breaking change to a predicate's meaning gets a new predicate name (or a new namespace for a systematic change), never a redefinition. This is what makes the "what did we believe on Aug 19" query survive five years of schema drift — it removes failure mode #7 above by construction. <https://github.com/matthiasn/talk-transcripts/blob/master/Hickey_Rich/Spec_ulation.md>, <https://blog.ezyang.com/2016/12/thoughts-about-spec-ulation-rich-hickey/>
8. **XTDB's `ASSERT <predicate>, '<message>'` transaction primitive.** A declarative precondition that rolls back the whole transaction with a custom message, with the failure recorded in the transaction table. This is how we implement "reject a write that would create an unresolved contradiction without an accompanying contradiction object." <https://docs.xtdb.com/reference/main/sql/txs.html>
9. **Datomic's excision-record-is-permanent rule.** GDPR erasure must leave an un-erasable tombstone so the system "strikes a delicate balance between forgetting and remembering that you forgot." <https://docs.datomic.com/operation/excision.html>
10. **Deterministic, immutable, self-describing storage files with min/max + bloom metadata**, so compute nodes need no inter-node coordination and cache invalidation is trivial ("superseded" is a well-defined predicate). <https://www.xtdb.com/blog/building-a-bitemp-index-3-storage>
11. **Nat Pryce's projection-as-read-through-cache framing.** Not "the projection is the read model" but "the projection is a cache of state derivable from the log, discardable and rebuildable at will, and the write path never updates it directly." That one rule kills failure modes #1, #2 and #5. <http://natpryce.com/articles/000819.html>
12. **Redis Streams' consumer-group mechanics as the webhook delivery model** — per-consumer pending-entries list, explicit ack, delivery counter, and `XAUTOCLAIM` for redelivering entries idle beyond a threshold. That is the correct shape for at-least-once webhook fanout regardless of which broker we pick. <https://redis.io/docs/latest/develop/data-types/streams/>

## What we should deliberately do differently, and why

1. **Do not build on RDF / RDF-star / SPARQL.** We should steal the nanopublication *shape* and reject its *substrate*. RDF 1.2 is still CR with a self-acknowledged vague reifier definition <https://github.com/w3c/rdf-star-wg/issues/169>, store support for SPARQL 1.2 triple terms is uneven <https://ontologist.substack.com/p/rdf-12-vs-neo4jopencypher>, vendors ship incompatible `urn:rdf4j:triple:` encodings <https://graphdb.ontotext.com/documentation/11.3/rdf-sparql-star.html>, and RDF-star's formal semantics asserts embedded triples — poison for a contradiction store. We want the four-part record as *columns and a JSONB evidence blob in a relational table*, not as quads.

2. **Contradiction detection must be a write-time constraint, not a batch job — and it is our actual differentiator.** No production system in this slice does it. Wikidata explicitly punts to talk pages <https://www.wikidata.org/wiki/Help:Ranking>. Nanopublications have no notion of it. Implement it as a partial unique index over `(scope, subject, metric)` restricted to live, non-superseded, non-deprecated records; a second live record for the same key either supersedes the first (explicit `supersedes` id) or the transaction fails an `ASSERT` and the writer must materialize a contradiction object. Model it on Datomic/XTDB's transaction-level assert, not on a TMS.

3. **Reject truth maintenance systems and AGM operators outright.** ATMS is 2^n <https://cis.temple.edu/~ingargio/cis587/readings/tms.html>, retraction dirties the whole network <https://www.academia.edu/16674638/An_assumption_based_TMS>, and AGM has no time dimension and a Recovery postulate that fails for belief bases <https://plato.stanford.edu/entries/logic-belief-revision/>. Take one idea from each and nothing else: from TMS, that a contradiction is a **first-class named object with a set of supporting assumptions** (a "nogood" you can point at); from AGM, that **expansion, contraction and revision are three different operations** and an API that conflates them is wrong. Our supersede-with-provenance is *expansion plus an explicit ordering assertion* — deliberately weaker than revision, and that weakness is the feature.

4. **Never let the event log be the public API.** Kiehl's coupling/opacity argument is decisive <https://chriskiehl.com/article/event-sourcing-is-hard>, and Pryce's team specifically regretted using the event store as a message bus <http://natpryce.com/articles/000819.html>. Downstream consumers (Linear, Discord, webhooks) subscribe to a **versioned, curated projection feed** with its own schema and compatibility contract, never to raw internal records. Corollary: the log carries only *business* facts. Delivery failures, retries, and heartbeats go somewhere else entirely — Pryce's team had to filter "attempt to send email failed with an IOException" out of user-facing history, and I'd rather never let it in.

5. **Do not use CRDTs for the fact store.** Automerge/Yjs auto-merge concurrent divergence <https://automerge.org/docs/reference/documents/>; we are being paid to *not* do that. Local worktree caches should be **read-through, immutable, content-addressed caches with an offline write queue**, not mergeable replicas. Offline writes replay against the single-writer log and are validated (including contradiction checks) on arrival — a write that would create an unresolved contradiction fails and surfaces to the agent, which is the correct behaviour and impossible with a CRDT.

6. **Do not use LISTEN/NOTIFY for fanout, even after the PG19 fix.** The lock is a global commit mutex in every released Postgres today <https://www.recall.ai/blog/postgres-listen-notify-does-not-scale>, and even fixed, notifications are non-durable, capped at ~8 KB, and lost on disconnect. Webhooks and agent heartbeats need durability and replay.

7. **Do not put per-worktree Neon branches in the design.** 10–25 branches/project by plan, 5,000 hard cap, $1.50/branch-month <https://neon.com/docs/introduction/plans>. Neon branching is superb for **preview environments and "give me the fact store as it was on Aug 19 to debug against"**, and that's the use we should make of it — a handful of long-lived branches, not hundreds of ephemeral ones. Per-worktree isolation is a local SQLite cache, which costs zero.

8. **Do not adopt XTDB or Datomic as the product's storage engine, despite both being better bitemporal engines than anything we'll build.** Reasons, in order: (a) neither enforces provenance, so we'd be building our validation layer anyway; (b) neither has contradiction objects, so we'd be building that anyway; (c) XTDB v2 has no independent safety audit and no published throughput number <https://docs.xtdb.com/intro/what-is-xtdb.html>; (d) Datomic's intra-transaction pseudo-write-skew <https://jepsen.io/analyses/datomic-pro-1.0.7075> is precisely the class of bug that would let a supersede and a contradiction commit together and corrupt our core invariant; (e) selling a product whose storage layer is a JVM database with a single transactor and a self-terminating heartbeat is an operational liability. **We should steal XTDB's index design and run it on Postgres.** If someone insists on an off-the-shelf bitemporal engine, XTDB v2 is the right one and its Postgres wire compatibility makes it a swappable back end later.

9. **Do not claim "immutable audit log" in marketing without the erasure caveat.** GDPR erasure is real and both prior-art systems treat it as a violent, out-of-band operation (Datomic: cost proportional to whole-DB size, avoid >few thousand datoms live <https://docs.datomic.com/operation/excision.html>; XTDB: a separate `ERASE` statement outside the normal DML <https://docs.xtdb.com/reference/main/sql/txs.html>). Design erasure in from day one as a distinct, audited, tombstone-leaving operation, and budget for its cost, rather than discovering it at the first enterprise security review.

10. **Do not let embedding-based retrieval share a return path with exact retrieval.** This is our stated thesis and the Wikidata/RQSS numbers support it: unenforced, unranked provenance decays to 0.58/1 quality over a decade of effort <https://www.semantic-web-journal.net/content/rqss-referencing-quality-scoring-system-wikidata>. Fuzzy results must be a separately-typed channel with a different response shape, so no caller can accidentally treat "close enough" as "measured".

### Recommended stack

**Postgres 17/18 as the single source of truth, one append-only `records` table, XTDB's index ideas applied inside it, NATS JetStream for fanout, SQLite for per-worktree caches.**

Concretely:

- **Store.** Managed Postgres (Neon on the Scale plan with scale-to-zero **disabled**, or plain RDS/Crunchy if the branching isn't worth the cold-start risk). One append-only, insert-only `records` table. Columns: content-hash id (PK), scope path, subject, predicate, value, `valid_from`/`valid_to`, `assert_time`, `supersedes` (nullable FK to id), `confidence` enum, `evidence` JSONB, `tx_id`. A `transactions` table carries batch-level provenance (agent id, mission, correlation id, SLSA-style resolved dependencies with git commit digests). `REVOKE UPDATE, DELETE` on `records` from the application role — mutation is denied by the database, not by discipline.
- **Bitemporal correctness.** Use PG18's `WITHOUT OVERLAPS` on `(scope, subject, predicate, valid_period)` for the live set — this is exactly the constraint that makes two live records for the same metric *impossible to insert*, which is how contradiction detection becomes free and mandatory <https://www.postgresql.org/docs/18/sql-createtable.html>. System-time is ours to maintain (PG18 has no system versioning), which is fine, because we're append-only: `assert_time` is set once on insert and never changes.
- **Sub-10ms hot reads.** A `live_records` partial index (`WHERE valid_to = 'infinity' AND superseded_by IS NULL AND rank <> 'deprecated'`) plus a `recency` column computed exactly as XTDB defines it, used as the leading partition/index key so as-of-now queries never touch historical partitions <https://www.xtdb.com/blog/building-a-bitemp-index-3-storage>. Partition `records` by the survivor/historical split. Hot-path reads are single-index lookups on a partial index over the live set — comfortably sub-10ms on warm Postgres, and unaffected by history volume.
- **Exact-first retrieval.** Structured predicates plus Postgres full-text (`tsvector`) on the same rows, in the same transaction, with the same visibility rules. Embeddings live in a **separate** table and a **separate** API returning a differently-typed response.
- **Fanout.** NATS JetStream. Subject hierarchy `facts.<org>.<project>.<mission>.<predicate>` — the wildcard model means new predicates need no stream reconfiguration <https://docs.nats.io/nats-concepts/jetstream/streams>. Durable consumers with explicit ack for webhook delivery, ephemeral consumers for agent liveness. Publish from a single outbox poller reading `records` by `tx_id`, **not** from `NOTIFY` inside the writing transaction <https://www.recall.ai/blog/postgres-listen-notify-does-not-scale>. If we want one less moving part, Redis Streams' consumer-group semantics are equivalent for our fanout scale <https://redis.io/docs/latest/develop/data-types/streams/>; JetStream wins on durability defaults and subject wildcards.
- **Per-worktree offline cache.** Embedded SQLite (or Turso's engine, which adds sync and an explicitly auditability-oriented agent state SDK <https://docs.turso.tech/introduction>). Cache is read-through and content-addressed: because record ids are content hashes, cache validation is an id comparison and there is no invalidation problem. Offline writes go to a local outbox and replay against Postgres, where they are validated (provenance present, no unresolved contradiction) on arrival. **No CRDT.**
- **Read-through sync to many clients (optional, later).** ElectricSQL over the same Postgres, since it works with any Postgres data model and puts shapes behind a CDN <https://electric.ax/docs/sync/guides/deployment>. Add it only once we have a dashboard that needs it; it introduces a stateful disk and an uncompacted shape log <https://github.com/electric-sql/electric/issues/1582>.
- **Rejected:** Convex (owns the transaction and reactivity model, cloud persistence is PlanetScale/MySQL <https://docs.convex.dev/understanding/overview>); D1 (10 GB hard cap, single-threaded <https://developers.cloudflare.com/d1/platform/limits/>); Durable Objects as the store (10 GB, ~1,000 req/s per object <https://developers.cloudflare.com/durable-objects/platform/limits/>) — though a DO per agent is a reasonable *registry/heartbeat* substrate; Datomic and XTDB as engines, for the reasons in point 8 above; anything RDF.

Why Postgres wins here: we need mandatory provenance validation, a write-time contradiction constraint, exact-first structured + FTS retrieval, and per-worktree offline caches. Three of those four are application-layer concerns we must build regardless of engine, and the fourth (the write-time constraint) is precisely what PG18's `WITHOUT OVERLAPS` gives us declaratively and no bitemporal engine gives us at all. Choosing a specialist bitemporal engine buys us the temporal index — which is the one part we now have a detailed public blueprint for — and costs us the constraint system, the ecosystem, the operational familiarity, and, in Datomic's case, an audited-and-documented intra-transaction anomaly aimed straight at our core invariant.
